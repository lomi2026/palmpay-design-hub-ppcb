## 4. 标准流程：逐关通过才前进

### G0：确认范围与基线

1. 阅读 00、05、06、15 及一页发布检查卡；按改动补读本文对应章节、PRD、ER、开发计划、设计决策。
2. 检查目录、分支、已修改和未跟踪文件，不覆盖他人工作。列明受影响页面、接口、实体、权限、配置和迁移。
3. 查 PPCB 身份、能力、实时健康、当前 testing/production 状态、最新受管源码及文件契约（涉及文件时）。只记录必要脱敏结果。
4. 明确这是代码发布、配置变更、业务内容操作还是迁移。通过应用修改内容/封面通常不需重建；配置重启按当前契约处理，不能冒充代码热更新。
5. 记录用户已授权的动作、环境、次数与失败处理。已有明确授权不重复询问；“整理规范”不包含线上操作授权。

放行证据：变更清单、源码基线、环境、授权范围、受影响数据和回退候选。

### G1：完成本地验证，冻结候选源码

- 按锁文件安装，保留项目 Node >=24 与 pnpm 约束；不要为发布顺手升级依赖。
- 前后端类型检查、Lint、相关单元/集成/E2E、构建、权限和差异审查。根目录 `pnpm test` 只跑 API，Web 必须另跑 `pnpm --filter @palmpay/web test`。
- 两套 PPCB 子路径 Web 构建均验证；检查实际运行时依赖追踪、相对软链接、Prisma/OpenSSL、启动入口和文件目录。
- 运行实际组装产物，使用一次性本地数据库分别验证空白测试与生产模式、已有数据升级、重复初始化；涉及并发初始化时验证锁和幂等。
- 核心数据库失败时健康检查必须失败；普通启动不触发文件迁移，不把健康当文件功能验收。
- 报告通过、失败和跳过数。被跳过的数据库测试不能算已通过；必要测试缺失则阻塞，不相关的环境型测试注明跳过原因。
- 只提交本次已验证变更，冻结候选 commit。打包前再次核对实际文件清单。

放行证据：候选 commit、验证结果、实际产物启动记录、已知限制。业务阻断项未解决不得上传试错。

### G2：生成唯一最小源码包并检查

使用现有 `pnpm ppcb:package`。仅在发布/交付打包已获授权时生成包；包保存于仓库外。

检查 ZIP 本身：

- 根目录含 Dockerfile、package.json、锁文件和 workspace 清单，无多余外层目录。
- 文件清单能支撑 API、Web、迁移与运行打包；无绝对路径、路径穿越或越界软链接。
- 无 `.env*`（包括 `.env.example`）、凭据、密钥、数据库、原始备份、导出附件、node_modules、构建缓存或 Git 元数据。
- 当前仓库已有五张获批迁移封面和内容快照，这是历史迁移特例，不能扩展为允许任意业务导出进入 Git/源码包。清点实际清单与授权；移出这些已跟踪材料属于独立变更，不能在复盘时擅自删除。
- 记录文件数、字节数、整包 SHA-256；解压校验通过。提交号与测试对象一致。

**现有脚本的边界：** 它从 HEAD 归档并检查已跟踪发布文件的 staged/unstaged 差异，执行 ZIP 完整性检查；未跟踪文件不会被收入也不会触发该差异检查，脚本没有全面敏感内容扫描。必须补做 `git status --short --untracked-files=all`、包清单和敏感文件检查，不能把脚本描述成完整安全门禁。

### G3：上传与平台预检

- ZIP 超过 5 MB 或可能造成上下文压力时使用分片上传；本项目约 6.7 MB 的历史包属于该路径，实际大小以本次输出为准。
- 从平台返回的 `maxChunkBytes` 选择片大小 C。对于 N 字节文件，片数为 ceil(N/C)，第 i 片取 `[i*C, min((i+1)*C,N))`，i 从 0 开始。整除时不产生空尾片。
- 发送前本地验证片号连续、无重复、无间隙，各片长度总和等于 N，重组哈希等于原包。Base64 只在工具调用边界生成并直接传参，禁止输出到对话或日志。
- `app_start_source_upload` → 顺序 `app_upload_source_chunk` → `app_complete_source_upload`。合并成功并核对大小/哈希后，用同一 uploadId 调用 `app_preflight_uploaded_source`。
- 小包可用 `app_preflight_source`，发布必须使用同一包。预检失败不得构建；警告逐条解释，不能把 localhost 占位配置等警告一概等同泄密或阻断。
- 最新 revision 若与本地基线不同，先做源码核对。409 冲突时停止覆盖，取得新版本并合并验证，不能只替换 baseRevision 再提交。

放行证据：包哈希、uploadId、预检通过、已解释警告、正确 baseRevision。失败后不自动创建新上传会话。

### G4：只发布一次测试候选并跟踪确切操作

测试发布参数沿用本项目：`targetEnvironment=testing`、端口 8080、健康路径 `/healthz`、启用托管数据库，传正确 baseRevision 与变更摘要。构建档位按已验证需求及当前平台契约选取。

- 记录 revisionId、buildId、operationId、releaseId；匹配本次对象，不能在整段历史响应里搜索“成功”作为结论。
- 分别确认源码构建终态、发布操作终态、当前服务指向的 release、实例就绪、入口可访问。`PUBLIC_READY` 标签单独出现不足以证明对应操作完成；以当前工具契约和匹配 ID 的最终结果为准。
- 短时等待后逐步降低查询频率，单次等待不超过 60 秒；约每分钟向用户说明有意义的进度，不反复输出未变化状态。
- 构建超过 15 分钟、发布超过 10 分钟且无阶段推进时读取诊断并报告阻塞；不能仅凭计时宣告已失败，也不自动重发。
- 构建失败取 build logs；启动/健康/路由失败取对应环境的 release diagnostics 和 runtime logs；数据库问题加查 schema 状态。尽早保留脱敏错误，避免清理后证据丢失。

放行证据：本次测试 release 真正运行、核心健康通过。此时仍不能晋级。

| 范围 | 最小验收内容 | 通过条件 |
|---|---|---|
| 入口与资源 | 首页、深层路由刷新、JS/CSS、图片、未知路径 | 内容/类型正确，无错前缀、跨环境跳转或假 200 |
| 登录 | 未登录跳转、真实员工返回原页面、Owner 身份与角色 | 不循环登录；不以“重定向正常”代替登录成功 |

| 核心流程 | 本次变更，加搜索/详情及受影响的草稿、发布、编辑、保存跳转 | 持久化正确，版本和审核规则保持批准行为 |

| 环境隔离 | 所有测试写操作 | 只写测试 schema/文件，临时草稿单独标记并记录清理情况 |

`app_test_request` 用于真实 testing HTTP/API；浏览器用于登录、文件选择、导航和回显。模拟文件服务只证明适配逻辑，不能替代真实 OSS。浏览器被工具策略阻断时写“未验证”，不要绕过限制或报成页面缺陷。缺失必要验收证据时保留待验收状态。

放行证据：测试清单、结果、失败为零的必要项目、验收数据处理记录及可审阅的生产影响说明。

### G6：生产确认、晋级和复核

向用户给出具体候选：测试 release、变更、已通过/未验证项、数据库与文件影响、配置差异、回退方式。已有明确覆盖该候选的生产授权可继续；否则在材料齐全后申请生产确认。

调用 `app_promote_test_to_production` 指定已验收 testing release；禁止重新上传、重新构建或把测试数据库复制到生产。记录生产 operation/release 及镜像标识，与测试镜像核对。

生产上线后核查实例、健康、真实入口、真实登录、关键页面及已有文件；仅在有已批准迁移时核对迁移计数。涉及生产写验收时明确测试数据及清理范围；不能把 testing 工具结果写成生产证据。没有真实登录会话时明确留为待验收。

生产尚未切流也可能已经执行迁移/导入。失败报告必须分别写服务版本、数据库和文件的影响，不能笼统写“线上未变化”。

### G7：交付与收尾

- 返回生产链接、release、访问范围、验证结果、残留限制，不只说“成功”。
- 更新 05 顶部当前摘要；稳定边界变化写入 15；详细历史保留原时间与被覆盖关系。
- 记录待处理的测试草稿、孤立文件与迁移事项。PPCB 当前适配没有对象删除闭环时，不把“解绑附件”描述成“物理删除 OSS 对象”。
- 原托管服务和 R2 仅在生产文件验收、备份确认且用户明确授权停用后处理。PPCB 已不需 R2 凭据，不等于原 R2 已关闭。

## 5. 数据、配置与回退专项规范

### 数据迁移

当前获批迁移基线为 48 条内容、49 个版本、17 个标签、5 张被引用封面；历史备份的 30 表/460 行、9 个导出对象不是当前应全量导入的清单。每次迁移重新核对授权范围与源快照，不把测试草稿、行为记录或其他历史用户一并导入。

日常代码发布默认零业务数据导入、零封面搬迁。结构迁移入口保留，按现有迁移账本/校验和跳过已完成项；没有新 migration 就不重复执行历史 SQL。

基础组织/角色/权限仅在目标组织不存在时，在同一事务及数据库锁内初始化；已有组织立即跳过，不重置名称、分类或权限。新环境默认空内容，若需要历史内容须另做获批迁移。组织已存在但基础配置缺失时应诊断后定点修复，不自动重跑 seed。历史内容/封面导入工具仍保留，但不是安全的通用重试入口，也没有新增自动迁移账本。

业务迁移与基础初始化分开核对。目标组织、用户按批准业务键映射并复用，外键引用实际目标 ID；不机械保留会冲突的环境内部 UUID。业务标识和原始内容关系按迁移方案保留。

幂等需同时证明“不重复”和“不覆盖后续编辑”。多实例/重启情况下核对并发锁、唯一键和失败续跑，非事务性文件上传失败可能留下对象，记录补偿范围。备份放仓库外并验证可恢复；未经明确授权不将生产数据复制到 testing。

### 配置与身份

数据库连接和 schema 使用平台注入值并校验应用归属；查询和迁移使用一致 search_path，按 PPCB 契约关闭 SSL，不抄原托管连接串。平台保留环境变量不得自行覆盖。

平台网关身份与应用 RBAC 都必须成立；不让浏览器伪造受信任身份头，不通过扩大权限掩盖 seed 或映射错误。`PPCB_INTERNAL_SECRET` 由现有运行时内部处理，不让用户在 Portal 填写它。

当前使用 `enterprise_login`：企业内有效员工可登录，普通员工以 PPCB `User` 进入。应用最终权限是 PPCB 转发权限与数据库角色权限的交集，因此两层必须使用同一权限键并同时满足。`User`、`Operator` 仅配置 `content.read`、`content.create`、`content.edit_own`、`ai.execute`；管理权限继续限制在 `Owner`、`Maintainer`。纯权限定义修改由平台实时配置生效，不重新构建镜像、不执行数据库迁移，但仍须在测试和生产分别核对运行时配置并用普通成员重登验收。

业务文件走 PPCB 私有文件能力，不要求另建 Bucket、配置 OSS 密钥。普通配置与 Secret 分离并按环境核查；平台运行时 Token、Cookie、签名 URL 不进源码、数据库长期字段、聊天或日志。公开路径和访问权限更改是独立动作，不能为排障擅自放开。

### 回退

发布前记录旧生产 release/镜像、数据库迁移兼容性、文件存储状态、备份位置与恢复验证。先确认平台当前支持的回退途径，不臆造 rollback 工具。

**旧生产/测试镜像仍包含自动导入逻辑，重启或回退可能覆盖后续编辑，不能列为无条件安全的回退候选。** 新版测试通过后，优先保留不含自动导入的兼容版本作为回退基线；首次切换若尚无此基线，生产前明确兼容性、备份和恢复措施，不通过试回退验证。

新旧实例可能短时共存，数据库变更应向后兼容。发生阻断时优先停止进一步切换；按已获授权和核实的能力恢复旧镜像。**镜像回退不会撤销数据库迁移、业务导入或 OSS 上传。** 数据恢复、破坏性逆迁移和对象清理由独立恢复方案控制，说明会影响的新写入，取得对应授权后实施。

## 6. 失败与协作规则

一次已授权测试发布出现异常或明确失败后，先冻结会扩大影响的同一步骤，不重复上传、合并、构建、发布或线上修复；保留失败步骤、脱敏证据和实际影响，继续只读状态与日志诊断，并向用户给出一个最小下一步或可选方案。预检阻断、revision 冲突和必要验证失败不能绕过。需要终止整次发布时先取得用户确认；若用户明确要求停止全部操作，连诊断也停止。

用户已经授权的发布范围在问题修复后仍然有效，不因一般异常自动失效；但新的环境、生产晋级、权限变更、数据恢复或其他扩大影响的动作仍需各自授权。不得以更新 Skill、报告 FAQ、创建应用或改权限等方式变相扩大范围。

PPCB Skill 默认要求主动提交平台 Issue/FAQ，但本项目已有明确的“先确认、不自动提交”约定，以用户约定为准。需要上报时先准备可审阅的脱敏内容。自动审批拒绝时原样概括被拒动作和原因，不绕过、不反复调用同一副作用接口。

失败归因先区分：上传校验、平台构建准备、依赖/镜像、应用编译、启动、数据库/seed、文件协议、网关身份、应用权限、浏览器路径。修复必须对应日志证据；相同错误没有新证据不重新试一次。
